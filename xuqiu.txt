可以。结合你现在做 **AgentOS** 的方向，我建议你不要把 ADK 当成“功能清单”照着实现，而是把它当成一个已经踩过大量坑的 **Agent Runtime 参考实现**。

我这次按 **Google ADK Java 1.8.0（2026-08-13）源码与官方文档** 来梳理。当前 Java 仓库 README 标注的版本就是 `1.8.0`。([GitHub][1])

# 一、先看 ADK 到底做了什么

一句话概括：

> **ADK = Agent 定义框架 + Agent Runtime + LLM 调度 + Tool Runtime + MCP + Workflow/Multi-Agent + Session/State/Memory + Artifact + HITL + Callback/Plugin + Event Stream + A2A + Skill + Code Executor + Streaming/Live + Observability + Dev UI + Evaluation。**

所以它绝不是：

```text
用户问题
   ↓
LLM
   ↓
Tool
   ↓
答案
```

而更接近：

```text
                       ┌──────────────┐
                       │ Application  │
                       │ Web / CLI    │
                       └──────┬───────┘
                              │
                              ▼
                    ┌──────────────────┐
                    │      Runner      │
                    │ Agent Runtime    │
                    └────────┬─────────┘
                             │
                    InvocationContext
                             │
              ┌──────────────┴──────────────┐
              │                             │
              ▼                             ▼
        ┌──────────┐                 ┌─────────────┐
        │  Agent   │                 │   Session   │
        └────┬─────┘                 │ State/Event │
             │                       └─────────────┘
             ▼
      ┌──────────────┐
      │   LLM Flow   │
      └──────┬───────┘
             │
      LlmRequest / Response
             │
             ▼
          Model
             │
        FunctionCall
             │
             ▼
      ┌──────────────┐
      │ Tool Runtime │
      └──────┬───────┘
             │
      ┌──────┼─────────────┐
      ▼      ▼             ▼
   Function MCP          AgentTool
    Tool    Tool            │
                           Agent
```

这张图基本就是你 AgentOS 后面应该逐渐演化出来的样子。

# 二、ADK 最核心的第一层：Agent 抽象

ADK 最基础的概念不是 LLM，也不是 Tool。

而是：

```java
BaseAgent
```

官方源码说明里明确写了，`BaseAgent` 是所有 Agent 的抽象基类，包含 Agent 的名称、描述、子 Agent，并定义了 `runAsync()`、`runLive()` 等执行入口。`LlmAgent` 则是最主要的具体实现。([GitHub][2])

可以理解为：

```text
BaseAgent
   │
   ├── LlmAgent
   │
   ├── SequentialAgent
   │
   ├── ParallelAgent
   │
   ├── LoopAgent
   │
   └── Custom Agent
```

这其实非常重要。

### BaseAgent

负责定义：

```text
我是谁
叫什么
描述是什么
有哪些子 Agent
如何运行
```

但是：

**BaseAgent 本身不等于 LLM Agent。**

这意味着 ADK 的设计思想是：

> Agent ≠ LLM。

比如：

```text
SequentialAgent
```

完全可以只是一个控制器：

```text
Agent A
   ↓
Agent B
   ↓
Agent C
```

它自己根本不需要调用大模型。

这点你 AgentOS 非常值得学。

你现在的：

```text
SupervisorAgent
RAGAgent
CodeAgent
ReportAgent
```

以后最好统一：

```java
public abstract class BaseAgent {

    private String id;

    private String name;

    private String description;

    private List<BaseAgent> subAgents;

    public abstract Flux<AgentEvent> run(InvocationContext context);
}
```

然后：

```text
BaseAgent
  ├─ LlmAgent
  ├─ SequentialAgent
  ├─ ParallelAgent
  ├─ LoopAgent
  ├─ SupervisorAgent
  └─ CustomAgent
```

而不是让：

```text
SupervisorAgent
RAGAgent
CodeAgent
```

各自实现一套运行逻辑。

# 三、真正的核心：Runner

如果只让我推荐你精读 ADK 一个类：

> **先读 Runner。**

官方项目说明直接把 `Runner` 定义为主要的 Agent 执行类；它接收：

```text
BaseAgent
BaseArtifactService
BaseSessionService
BaseMemoryService
```

并提供 Agent 的运行入口。([GitHub][2])

也就是说：

```java
Runner
```

才是真正的 Agent Runtime。

不是：

```java
LlmAgent.run()
```

自己把所有东西干完。

它大致承担：

```text
接收用户输入
        ↓
查找 Session
        ↓
恢复上下文
        ↓
构造 InvocationContext
        ↓
确定从哪个 Agent 开始/恢复
        ↓
执行 Agent
        ↓
接收 Event
        ↓
保存 Event
        ↓
合并 StateDelta
        ↓
处理 Callback / Plugin
        ↓
处理 HITL
        ↓
返回 Streaming Events
```

这就是为什么你 AgentOS 的：

```text
AgentRuntime
```

非常重要。

### AgentOS 建议

你现在的：

```text
agentos-kernel

AgentRuntime
AgentScheduler
AgentLifecycle
AgentContext
```

方向没问题。

但我建议逐渐演变为：

```text
agentos-kernel
│
├── AgentRunner
│
├── InvocationContext
│
├── AgentEvent
│
├── EventActions
│
├── RunConfig
│
├── ExecutionBudget
│
├── RunOutcome
│
└── lifecycle
```

其中：

```text
AgentRunner
```

应该成为全系统真正的执行入口。

以后：

```java
agent.run()
```

尽量不要让业务直接调用。

而是：

```java
runner.run(request)
```

Runner 再：

```java
agent.run(invocationContext)
```

# 四、InvocationContext：一次 Agent 执行的“世界”

这个设计我尤其建议你 AgentOS 学。

不要不停地：

```java
method(
   userId,
   sessionId,
   toolRegistry,
   model,
   memory,
   state,
   callback,
   config,
   ...
)
```

而应该产生：

```java
InvocationContext
```

可以理解成：

> **本次 Agent Invocation 的运行环境。**

例如：

```java
public class InvocationContext {

    private String invocationId;

    private String userId;

    private String sessionId;

    private BaseAgent agent;

    private Session session;

    private RunConfig runConfig;

    private ToolRegistry tools;

    private MemoryService memory;

    private ArtifactService artifacts;

    private ExecutionBudget budget;

    private CancellationToken cancellationToken;
}
```

整个执行链：

```text
Runner
  │
  └─ InvocationContext
        │
        ├─ Agent
        ├─ LLM Flow
        ├─ Tool
        ├─ Callback
        ├─ Memory
        └─ SubAgent
```

都使用它。

你现在 AgentOS 里的：

```text
AgentContext
```

建议就朝这个方向演进。

甚至建议改名：

```text
AgentContext
      ↓
InvocationContext
```

因为它不是描述 Agent 本身。

而是描述：

> 这一次运行。

# 五、Event：ADK 一个非常漂亮的设计

这是我认为 AgentOS **必须借鉴** 的东西。

Agent 执行不是：

```java
String answer = agent.run(question);
```

而是不断产生：

```text
Event
Event
Event
Event
...
```

Session 本身也是由按时间排列的 Events 构成。官方文档明确把 Session 描述为单次对话线程，其中保存消息和 Agent 行为形成的事件序列。([Google GitHub][3])

例如：

```text
USER_MESSAGE
      ↓
LLM_START
      ↓
LLM_RESPONSE
      ↓
TOOL_CALL
      ↓
TOOL_RESULT
      ↓
STATE_DELTA
      ↓
AGENT_TRANSFER
      ↓
LLM_RESPONSE
      ↓
FINAL_RESPONSE
```

所以 UI 才能显示：

```text
● 正在思考
✓ 分析需求
● 调用 WeatherTool
✓ WeatherTool 完成
● 生成最终答案
✓ 完成
```

你之前问我：

> Codex 那种计划执行完会打勾，是 React 实现的吗？

现在可以更准确地说：

**React 只负责展示。真正的数据源应该是 Runtime Event。**

比如 AgentOS：

```java
public record AgentEvent(
    String eventId,
    String invocationId,
    String sessionId,
    String agentId,
    EventType type,
    Object data,
    EventActions actions,
    Instant timestamp
) {}
```

前端：

```text
SSE/WebSocket
     ↑
AgentEvent
     ↑
AgentRunner
```

这样：

```text
PLAN_CREATED
PLAN_STEP_STARTED
TOOL_CALL_STARTED
TOOL_CALL_COMPLETED
PLAN_STEP_COMPLETED
AGENT_TRANSFERRED
RUN_COMPLETED
```

React 根据事件更新 UI。

这才是正确架构。

# 六、EventActions / StateDelta

ADK Event 还不只是日志。

Event 会携带：

```text
Actions
State changes
```

比如：

```text
stateDelta
endOfAgent
transfer
escalation
```

ADK 最近多个版本甚至专门修过：

```text
stateDelta
parallel stop
parent session state
```

之类的问题；例如 1.7.1 修复了并行场景中 `endOfAgent` 合并，1.2.0 增强了子流程 state delta 向父 session 的传播。([GitHub][4])

这是非常有价值的设计：

```text
Event
=
发生了什么
+
系统状态应该怎么改变
```

而不是直接：

```java
session.setXXX()
```

AgentOS 可以设计：

```java
AgentEvent {
    EventPayload payload;
    EventActions actions;
}
```

其中：

```java
EventActions {

    Map<String,Object> stateDelta;

    String transferToAgent;

    boolean endAgent;

    boolean endInvocation;

    boolean requireApproval;
}
```

这会让 Runtime 非常干净。

# 七、Session / State / Memory 是三个东西

ADK 对这三个概念划分得非常明确。

官方定义是：

| 概念      | 作用                |
| ------- | ----------------- |
| Session | 一次持续对话            |
| State   | 当前 Session 的结构化状态 |
| Memory  | 跨 Session 可搜索记忆   |

([Google GitHub][3])

很多自研 Agent 最大的问题是：

```text
ChatHistory = Memory
```

全混一起。

ADK 没这么做。

### Session

例如：

```text
sessionId = S001
userId = U001

events:
 user: 重庆天气
 agent: ...
 tool_call: weather
 tool_result: ...
 agent: 28℃
```

### State

类似：

```json
{
  "city": "重庆",
  "unit": "celsius",
  "taskId": "T10001"
}
```

属于：

```text
当前执行状态
```

### Memory

比如：

```text
用户以前偏好摄氏度
用户常问重庆天气
过去一次任务结果
长期知识
```

MemoryService 则负责把信息存进去以及搜索。官方明确将 Memory 定义成跨会话可搜索的信息存储。([Google GitHub][3])

### AgentOS

因此你原来的：

```text
ShortMemory
LongMemory
VectorMemory
```

我建议调整一下。

不要把：

```text
SessionHistory
```

叫 `ShortMemory`。

更合理：

```text
agentos-session
│
├── Session
├── SessionState
├── SessionService
└── EventStore

agentos-memory
│
├── MemoryService
├── MemoryEntry
├── MemorySearchResult
├── InMemoryMemoryService
└── VectorMemoryService
```

即：

```text
Conversation Context ≠ Long-Term Memory
```

# 十、MCP：ADK 怎么设计

ADK 并没有把 MCP 当成 Agent Runtime。

而是：

> **把 MCP Server 暴露出来的工具适配为 ADK Tool。**

基本模型：

```text
LlmAgent
   │
   ▼
BaseTool / Toolset
   │
   ▼
McpTool
   │
   ▼
McpSessionManager
   │
   ▼
MCP Transport
   │
 ┌─┴──────────┐
stdio      Streamable HTTP
   │
   ▼
MCP Server
```

当前 Java 版本有 `McpToolset`、`McpSessionManager` 等组件；最近版本还持续修正 Streamable HTTP 子路径、stdio 参数、Claude MCP schema 等兼容问题。([GitHub][5])

所以你 AgentOS：

```text
MCPClient
```

不要写成：

```java
MCPClient.callTool()
```

然后 Runtime 特判：

```java
if (tool instanceof MCP...)
```

更推荐：

```text
                 AgentTool
                    ▲
         ┌──────────┼───────────┐
         │          │           │
 FunctionTool    McpTool     AgentAsTool
                    │
               MCPClient
                    │
             MCPTransport
```

Runtime 永远只知道：

```java
AgentTool
```

不知道 Tool 来自：

```text
Java
MCP
OpenAPI
Remote
Agent
```

这是解耦关键。

# 十二、LLM Flow：这是 ADK 源码另一个重点

很多 Agent 框架写成：

```java
model.chat(messages);
```

ADK 在中间又加了一层非常重要的：

```text
LLM Flow
```

大体：

```text
Agent
 ↓
BaseLlmFlow
 ↓
构造 LlmRequest
 ↓
Processors
 ↓
Model.generate()
 ↓
LlmResponse
 ↓
FunctionCall?
 ↓ yes
Tool Execution
 ↓
FunctionResponse
 ↓
重新调用模型
```

也就是你一直在研究的：

```text
Reason
→ Act
→ Observe
→ Reason
→ Act
→ Observe
```

只是 ADK 没必要直接把它叫：

```text
ReAct
```

而是 Runtime Flow。

你 AgentOS 当前最需要防止的问题就是：

```java
while(...) {

    model.generate();
```

全部写在：

```text
AgentRuntime
```

里面。

最后一定会越来越长。

可以参考 ADK 拆：

```text
    MemoryProcessor
    FunctionCallProcessor
    ConfirmationProcessor
```

这样整个模型调用生命周期可插拔。

# 十四、Multi-Agent

ADK 是真正把多 Agent 纳入核心模型的。

> 可以通过组合多个专用 Agent 构建层级化 Multi-Agent 系统。([GitHub][1])

## LLM 驱动协作

例如：


## Workflow Agent

例如：


### ParallelAgent


Java ADK 过去甚至专门修过 ParallelAgent 真正并行执行的问题，目前 changelog 已记录 parallel agent/tool execution 的相关修复。([GitHub][4])

### LoopAgent

```text
Agent
 ↓
判断
 ↓
继续
 ↓
Agent
 ↓
...
```

直到：

```text

end
maxIterations
```

# 十七、HITL：Human In The Loop

Java ADK 已经正式加入 HITL/Trace 相关支持，1.1.0 changelog 明确记录了 HITL；之后又持续修复 workflow sub-agent HITL 恢复、SequentialAgent resume 等细节。([GitHub][4])

它不是简单：

```java
Scanner.nextLine()
```

而是：

```text
Tool Call
   ↓
Requires Confirmation
   ↓
生成 Event
   ↓
Runtime Pause
   ↓
保存 Session
   ↓
用户批准
   ↓
新的请求进入 Runner
   ↓
找到原 Agent
   ↓
恢复原 ToolCall
   ↓
继续执行
```

这里非常值得你研究。

因为真正生产级 HITL 的难点不是：

```text
弹审批框
```

而是：

> **暂停后如何恢复执行。**

这涉及：

```text
session
event
toolCallId
originatingAgent
invocation state
resume point
```

AgentOS 最后也应该是：

```text
RUNNING
   ↓
WAITING_APPROVAL
   ↓
SUSPENDED
   ↓
RESUMING
   ↓
RUNNING
```

而不是线程一直：

```java
wait()
```

等用户批准。

# 十八、Callback

ADK 有多层 Callback 思想。

比如可以围绕：

```text
Agent
```


这对于 AgentOS 很重要。

```java
   saveAudit();
```

应该：

```text

 ↓

 ├─ TracePlugin
 ├─ MetricsPlugin
```

# 二十四、A2A

MCP 和 A2A 千万不要混。

```text
MCP
Agent → Tool
```

而：

```text
A2A
Agent → Agent
```

ADK 官方把 A2A 用来：

> 本地 Agent 与远程 Agent 协作，并允许把自己的 Agent 暴露给远程 Agent。([Google GitHub][7])

结构：

```text
AgentOS
   │
   │ A2A
   ▼
Remote Agent
   │
   ├─ own LLM
   ├─ own tools
   ├─ own memory
   └─ own runtime
```

而不是：

```text
AgentOS
 ↓
Remote Tool
```

最新 Java ADK 1.8.0 的大量 bug fix 都还集中在 A2A metadata、stream、terminal states、错误信息泄露等方面。([GitHub][4])

这说明：

> A2A 在真正工程里远比“HTTP 调一下另一个 Agent”复杂。

AgentOS 暂时不用急。

你的顺序最好还是：

```text
单 Agent
→ Tool
→ Memory
→ Planning
→ HITL
→ Workflow
→ Multi-Agent
→ A2A
```

# 二十九、ADK 当前仍然有哪些工程问题值得 AgentOS避坑

看 changelog 特别有价值，因为它告诉你的不是“ADK 有什么功能”，而是：

> **Agent Runtime 真正难在哪里。**

你会发现最近一直修：

```text
Runner race condition
Session stale state
Sequential Tool execution race
Parallel execution
HITL resume
Function call ID
Streaming FunctionCall
MCP schema
State propagation
A2A streaming
Event merge
Tool confirmation ownership
```

例如 1.5.0 专门修复“Runner 必须等待当前 step 的 events 落库之后，下一步 flow 才继续”，就是典型的 Agent Runtime 并发一致性问题；1.4.0 又修了并行 Tool execution、HITL 回到正确 sub-agent 等。([GitHub][4])

这对 AgentOS 是个非常大的提醒：

```text
Agent 开发难点

不是：

怎么调用 LLM

而是：

执行状态一致性
并发
恢复
事件顺序
工具调用归属
Session持久化
错误处理
超时
取消
HITL恢复
```

甚至截至 2026 年 7 月，Java ADK 还有用户提出缺乏完整 Run Cancellation/Abort 支持的问题。([GitHub][10])

这个 AgentOS 我建议你反而早做：

```java
CancellationToken
```
